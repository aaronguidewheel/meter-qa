Meter QA, version 2.0

What the agent does, step by step. Tap any box to open its details. It only reads: it never saves, clicks or types inside a meter.

Start: the user types /meter-qa
Safety: this agent can only look, never change anythingtap for details

The agent opens pages and reads them. That is all it does.

If anything tries to click, type, save or reset inside a meter or in Panopticon, a safety lock stops the run right away and tells the user what was blocked.

The agent never types, reads or keeps a password. The user signs in to each meter and to Panopticon by hand.

1Ask the user: What kind of meters are we checking?tap for details
CT meter. A meter with one current transformer (CT) sensor. A CT clamps around a machine's power wire and measures the electrical current. It has a written register standard.
Pulse meter. A trigger and reject meter. Two pulse sensors count items passing by (for example good and rejected bottles) and connect to the meter through a sensor hub. It has a written register standard.
Something else. Any other sensor setup, including more than one CT sensor on a meter. No register standard is written for it, so the agent asks the user, one question at a time: which sensors and ports, which register names, which formulas. It reads the answers back as a table, the user confirms, and the table is used for this run only.

Why it asks: each type has different rules. One box is checked as one type, never both.

2Ask the user: Do the meters share power with their machines?tap for details
Shared power. The meter is wired to the same electrical supply as the machine it watches. When the machine is off, the meter has no power and goes offline.
If yes. An offline meter is normal. It is reported as "offline, expected", with no flag.
If no. An offline meter is a problem. It is reported with a 🚩 red flag.
3Ask the user for the list of meters (or a starting file)tap for details
Meter list. One row per meter: the four-digit meter number, the line it sits on, its Panopticon meter name, and its box type (CT or pulse).
Starting file. A sheet or note that already has those columns. The user can paste it, type it or attach it.

If a column is missing, the agent asks one question at a time.

4Read the Guidewheel hardware and meter guidestap for details
Standards. The written rules for how a meter should be set up: clock and time server, Data Sharing, registers, sensors and naming. They are global for the team, so there is no separate file to fill in.
Where they live. The Solutions Consulting guides in Confluence: General Meter Configuration, Pulse Sensor Configuration, CT Sensor Installation, eGauge Hardware and Meter Troubleshooting. If Confluence is not connected, the agent uses a built-in copy taken from those guides on 2026-11-23.
If something is not written. The agent prints what it sees and says "observed, no standard". It never invents a rule. Right now this applies to any meter type other than one CT sensor or two pulse sensors: the agent asks the user instead.

5Read the meter and Panopticon parameterstap for details
Clock. The Date & Time page: time zone and time. A brand-new meter shows time zone "custom" with UTC. If that is still there, the clock was never set, and it gets a 🚩.
Registers. The Installation table: the named values the meter calculates, such as current, voltage, power and pulse counts.
Sensors. The CTid page: the sensor model each port recognized. The agent waits and reloads once before calling it empty.
General Settings. Data Sharing, the API URL, how often data is sent.
Connection. Whether the meter is on Ethernet or Wi-Fi, which network it joined, and the signal strength. Only a weak signal (below 50%) gets a 🚩. The agent never joins or changes a network.
Panopticon. The meter record and its log. Also the API URL shown by Show API, the web address Panopticon creates for each new device. It has the same shape for every meter (api host, /v2/ingest, vendor=egauge) and only the device number changes. The meter's Data Sharing address must match it exactly.

Reads only. Nothing is changed.

6Compare with the Guidewheel standardstap for details

A difference from the written guides, or from the other meters of the site, gets a 🚩.

A sensor on an unusual port is fine when CTid recognizes it. Sensor amps against machine load are not checked.

Register names chosen by hand are trusted. A typo in one is reported as a note, never "fixed".

7Save the raw output to an evidence filetap for details
Evidence file. A file the agent writes in the current folder: meter-qa-evidence/site-date.md. It holds the exact script output, the meter URL and the time with time zone.

No evidence entry means no verdict for that meter.
